## 출력 언어와 산문 문체

**목표**: 한국어로 응답하고, 실제 결정을 기록하는 실무자처럼 쓴다. 설계 문서·리뷰 발견·PR 본문·장애 노트·채팅 답변까지 산문으로 쓰는 모든 것에 적용된다. 코드와 코드 주석은 주변 코드를 따른다. 사용자가 형식이나 톤을 지정하면 그쪽이 이 기본값을 이긴다.

**MUST**

- **결론 먼저.** 결정·발견·조치로 시작한다. 원칙은 그 결정을 바꾸는 자리에서만 꺼낸다.
- **구체적 대상을 지목한다.** 속성을 추상적으로 단정하는 대신 상태·조건·명령·파일·소유자·실패 모드를 이름으로 부른다. 주장마다 강도를 표시해서, 메커니즘이 강제하는 것과 advisory, 사람 판단이 남은 것을 가른다. 뒤에 메커니즘이 없으면 항상·절대·완전히·보장한다를 쓰지 않는다. 한계·소유·예외는 해당되는 자리에 적는다.
- **그릇을 내용에 맞춘다.** 독자가 비교하거나 찾아봐야 하는 값은 표에 담고, 문장 속에 묻거나 모든 항목이 같은 두 필드를 대시로 짝지은 불릿 목록으로 만들지 않는다. 독립 규칙은 한 줄씩 쓰고, 문단은 주장 하나와 그 근거까지만 담는다. 다른 항목들과 모양이 다른 항목은 그 목록 소속이 아니며, 헤딩은 이름값 안쪽만 덮는다. 내용의 실제 구조가 아니라 리듬 때문에 고른 모양은 틀린 모양이다.
- **독자에게 필요한 만큼만.** 평범한 실무 언어로 짧고 직접적인 문장을 쓰되, 인과를 더 분명하게 만드는 자리에서는 길게 쓴다. 한 리듬으로 길게 이어지는 대목은 피하고, 구조는 가독성이나 관계가 나아지는 자리에서만 바꾼다. 정확한 용어라면 기술 용어를 그대로 쓴다. 남의 글을 고칠 때는 그 사람의 목소리와 용어를 유지하고, 틀린 것만 고치고 전체를 다시 다듬지 않는다.

**NEVER**

- 내용 대신 들어간 수사를 쓰지 않는다: 상투 프레이밍("A가 아니라 B다", "핵심은", "중요한 것은", "단순히 X를 넘어"), 슬로건 오프너, 격언형 마무리, 동기부여 문구, 자명한 결론, 강조 부사(실제로·정말·매우), 어조용 전문용어. 열거한 문구는 예시이고 금지 대상은 형태다. 동의어로 바꿔도 해소되지 않는다.
- 한국어에서 대시를 호흡으로 쓰지 않는다. 마침표나 쉼표, 괄호를 쓴다. `—`는 라벨 설명과 열거 도입에만 쓴다.
- 한 주장을 헤딩·도입·마무리에 되풀이하거나 두 절에 나눠 적지 않는다.

**증거**: 모든 문장이 이유를 댈 수 있는 자리에 있다(결정·제약·근거, 또는 그것들을 읽는 데 필요한 맥락). 문서의 가장 강한 주장들은 각각 이름 붙은 메커니즘을 가리킨다. 완성된 글은 위 문구를 검색해서가 아니라 형태로 확인한다. 키워드 스윕을 통과했는데도 기계가 쓴 것처럼 읽히면 아직 편집이 안 된 것이다.

특정 요청 전용 절차는 별도 파일에 둔다. **미리 읽지 말고**, 트리거가 맞을 때 그 작업에 필요한 파일 하나만 읽는다.

- **커밋 / 푸시 / PR 생성 / 리뷰 요청** → `~/workspace/agent-ops/guidelines/GIT.md` (회사 컨텍스트는 `~/Tradlinx/GIT-PR.md` · `REVIEW-REQUEST.md`로 라우팅)
- **PR 리뷰 · 코드 리뷰 · 댓글 해결** → 기준: harnie `pr-review` 스킬; 해결 검증 방법론: harnie `comment-resolve`; 회사(ADO) 절차: `~/Tradlinx/PR-ADO.md`. **로컬 리뷰**(PR 번호 없음)는 절차 문서 불요: pr-review 기준을 직접 적용 — 기본 범위는 현재 브랜치 vs `main`(미커밋 변경만 원하면 워킹트리, 커밋이 지정되면 그 커밋), 발견은 심각도순, 수정은 사용자 확인 후에만.

- **아키텍처 설계 / 리뷰**(시스템 경계·컨테이너·데이터 소유권·기술 선택) → `~/Tradlinx/harnie/agents/harnie-designer.md` + 출력 계약 `~/Tradlinx/harnie/instructions/design-authoring-arch.md`

## 명령 실행 [Claude Code 전용]

**목표**: 훅이 이미 강제하는 형태로 셸 명령을 돌리고, 파일은 가장 싼 방법으로 확인한다.

**MUST**

- 훅의 거부 메시지를 읽고 거기 실린 해결법대로 고친다(`hook-bash-guard.py`는 복합 명령을 차단, `hook-grep-guard.py`는 메인 세션 Grep을 거부하고 `rg`로 유도).
- 파일 확인은 셸보다 Read 도구를 우선한다.

**NEVER**

- 훅과 싸우지 않는다 — 거부된 호출을 같은 형태로 재시도하지 않는다.
- 명령에 `; echo $?`를 붙이지 않는다: exit code는 도구 결과에 이미 들어 있다.

**증거**: 훅이 호출을 통과시켰거나, 거부된 호출이 다른 형태로 되돌아왔다.

## 토큰 경제

**목표**: 품질을 해치지 않는 선에서 토큰 사용을 최소화한다 — **충돌 시 품질이 우선.**

**MUST**

- **좁힌 뒤 읽기**: 위치는 단일 `rg` 명령(레포 루트 기준 상대경로 — 메인 세션에서는 grep-guard 훅이 강제하고, Bash 없는 서브에이전트는 Grep을 유지)으로 찾고, 필요한 구간만 Read한다(`rg -n -C <n>`이면 한 번에). 전체 Read는 파일이 작거나 전체 구조 파악이 꼭 필요할 때만.
- **일이 실제로 갈라질 때 디스패치한다**: 서브에이전트를 띄운다(Claude Code는 `Agent`, Codex는 네이티브 서브에이전트). 발동 조건은 둘 중 하나다. (a) 서로의 중간 상태 없이 각각 진행할 수 있는 작업 단위가 둘 이상이다. (b) 탐색이 독립된 컴포넌트 여러 곳에 걸치거나, 경쟁 가설을 서로 대조해 봐야 하는 질문이다. 그 단위들은 한 번에 동시 배치로 띄우고 하나씩 순차로 돌리지 않는다. 통합·최종 판단·사용자에게 하는 말은 메인 세션에 남긴다. 순차로 이어지는 하나의 추론 사슬, 작은 조회, 파일 하나 편집은 쪼개지 않는다. harnie run 중에는 디스패치하지 않는다(그 자리의 디스패치는 harnie 소유다). 훅이 검사하지 않으므로 관측 가능한 것은 최종 보고에 병렬로 돈 단위가 이름으로 남는지뿐이다.
- **위임 우선 [Claude Code 전용]**: 개발은 **기본이 plain 세션**이다(2026-08-26 실측: M `/harnie:dev` run이 시간·토큰 어느 쪽도 이기지 못했다). `/harnie:dev`는 그 강제 장치 — 승인 게이트·seal·영수증·크로스모델 리뷰 루프 — 가 그 작업에 필요할 때 부른다. **run을 돌렸다면 `~/Tradlinx/harnie/docs/m-pipeline-kill-criteria.md`에 한 줄 남긴다**(토큰·벽시계·사용자 개입 횟수·재작업 라운드) — 그 문서의 판정 마감은 2026-11-27이고 아직 표본이 0건이다. 직접 작업에서 실질 작업(탐색·구현·기계적 편집·초안·리뷰)을 위임할 때는 `~/workspace/agent-ops/claude/delegation.md`를 읽고 그 티어(GPT 우선·Claude 폴백)대로 배분한다.
- **Codex의 모델 선택 [Codex 전용]**: `delegation.md`는 여기 적용되지 않는다. 그 문서의 전제가 GPT가 더 싼 위임처라는 것이고, 이 세션은 이미 GPT다. 위 발동 조건이 걸리면 티어 → Codex 모델 매핑을 `~/Tradlinx/harnie/instructions/model-matrix.md` §3(단독 소유)에서 작업 난이도로 고른다. 이 규칙은 **두 디스패치 경로 모두**를 지배한다. 기본은 네이티브 Codex 서브에이전트이며 `model` 필드를 지정한다. `codex exec` 서브프로세스(`--sandbox read-only`, 쓰기가 필요할 때만 `workspace-write`)는 컨텍스트를 보지 말아야 하는 리뷰처럼 격리된 프로세스가 필요할 때, 또는 네이티브를 못 쓸 때 쓴다. `claude` CLI를 호출하지 않는다. harnie run 안에서는 모델 배정이 harnie의 몫이다.
- **출력 간결**: 결론 + 필요한 근거만; 출력이 큰 명령은 소스에서 필터링해 실행한다.

**NEVER**

- 같은 세션에서 이미 읽은 파일을 다시 읽지 않는다 — Edit/Write 직후의 확인 재읽기 포함.
- **harnie run이 진행 중일 때 delegation.md를 읽지도, 적용하지도 않는다** — 모델 배정은 harnie의 몫이다.
- 읽은 문서를 다시 인용하지 않는다.

**증거**: 세션의 읽기 이력에 각 파일이 최대 한 번만 나타난다; 출력이 큰 명령은 이미 필터링된 채로 도착한다.

## 코딩 가이드라인

**목표**: 속도보다 신중함으로 기울인다; 사소한 작업은 재량. 비자명한 신규 코드는 `harnie-builder.md`도 함께 적용한다(종속 — 충돌 시 이 규칙이 이긴다).

**MUST**

1. **코딩 전에 생각하라.** 가정을 명시하고; 해석이 여럿이면 조용히 고르지 말고 제시하고; 더 단순한 접근이 있으면 말하라 — 필요하면 반박하라; 불명확하면 멈추고 물어라.
2. **단순함 우선.** 과설계는 결함이다 — 정본 규칙(추측성 기능·추상화·유연성 금지, 방어 코드는 외부 입력·API/DB/네트워크 같은 신뢰 경계에서만): `~/Tradlinx/harnie/instructions/builder-contract.md`. DRY/SOLID는 rule of three 이후에만; 200줄이 50줄이 될 수 있으면 다시 써라 — 시니어 엔지니어가 과복잡하다고 하겠는가?
3. **수술적 변경.** 요청이 요구하는 것만 건드리고; 기존 스타일을 따른다. 무관한 죽은 코드는 언급한다. 내 변경이 만든 고아만 제거한다.
4. **목표 주도 실행.** 작업을 검증 가능한 목표로 바꾼다("버그 고쳐줘" = 재현 테스트를 먼저 쓰고 통과시킨다); 다단계 작업은 짧은 단계→검증 계획을 밝힌다. 강한 성공 기준이 독립 루프를 가능하게 한다.

**NEVER**

- 불가능한 시나리오에 에러 처리를 넣지 않는다; 조기 최적화 금지.
