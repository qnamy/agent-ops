## 작업별 참조 문서 (트리거를 만나면 그 파일을 읽고 그대로 수행)

특정 요청 전용 절차는 별도 파일에 둔다. **미리 읽지 말고**, 트리거가 맞을 때 그 작업에 필요한 파일 하나만 읽는다.

- **커밋 / 푸시 / PR 생성 / 리뷰 요청** → `~/workspace/agent-ops/guidelines/GIT.md` (회사 컨텍스트는 `~/Tradlinx/GIT-PR.md` · `REVIEW-REQUEST.md`로 라우팅)
- **PR 리뷰 · 코드 리뷰 · 댓글 해결** → 기준: harnie `pr-review` 스킬; 해결 검증 방법론: harnie `comment-resolve`; 회사(ADO) 절차: `~/Tradlinx/PR-ADO.md`. **로컬 리뷰**(PR 번호 없음)는 절차 문서 불요: pr-review 기준을 직접 적용 — 기본 범위는 현재 브랜치 vs `main`(미커밋 변경만 원하면 워킹트리, 커밋이 지정되면 그 커밋), 발견은 심각도순, 수정은 사용자 확인 후에만.
- **비자명한 신규 코드**(새 기능·모듈·복잡 로직) → `~/Tradlinx/harnie/agents/harnie-builder.md` (아래 §코딩 가이드라인에 종속; 직접 작업 시 루프 전용 부분은 무시)
- **아키텍처 설계 / 리뷰**(시스템 경계·컨테이너·데이터 소유권·기술 선택) → `~/Tradlinx/harnie/agents/harnie-designer.md` + 출력 계약 `~/Tradlinx/harnie/instructions/design-authoring-arch.md`
- **상세 설계 / 리뷰**(특정 서비스·모듈·API·DB·구현 로직) → 같은 디자이너 게이트 + 출력 계약 `design-authoring-detail.md`
- **설계 라우팅**이 일반 리뷰 트리거보다 우선; 고도가 모호하면 대상을 1회 확인. 직접 작업에서는 harnie 루프 전용 섹션을 무시하고, 설계 산출물은 한국어로 쓴다.

## 명령 실행 [Claude Code 전용]

셸 규칙은 훅이 강제하고 거부 메시지에 해결법이 실려 있다(`hook-bash-guard.py`: 복합 명령, 따옴표 밖 `;`/`&&`/`||`·명령치환·백틱 차단; `hook-grep-guard.py`: 메인 세션 Grep을 거부하고 `rg`로 유도). 훅을 우회하지 말고 따른다:

- Bash 호출당 단일 명령 하나. 진짜 복합·여러 줄 작업은 먼저 `.sh`/`.py` 파일로 Write 후 실행한다(개행+`#` 주석이 든 인라인 `python3 -c`는 절대 자동승인되지 않는다).
- 파일 확인은 셸보다 Read 도구를 우선한다; 명령의 exit code는 도구 결과에 이미 나오므로 `; echo $?`를 붙이지 않는다.

## 토큰 경제

품질을 해치지 않는 선에서 토큰 사용을 최소화한다 — **충돌 시 품질이 우선.**

- **좁힌 뒤 읽기**: 위치는 단일 `rg` 명령(레포 루트 기준 상대경로 — 메인 세션에서는 grep-guard 훅이 강제; Bash 없는 서브에이전트는 Grep 유지)으로 찾고, 필요한 구간만 Read한다(`rg -n -C <n>`이면 한 번에). 전체 Read는 파일이 작거나 전체 구조 파악이 꼭 필요할 때만. 같은 세션에서 이미 읽은 파일은 재읽기 금지 — Edit/Write 직후 확인 재읽기 포함.
- **위임 우선 [Claude Code 전용]**: 개발 작업은 가급적 harnie(`/harnie:dev*`)로. harnie 밖 직접 작업에서 실질 작업(탐색·구현·기계적 편집·초안·리뷰)을 위임할 때는 `~/workspace/agent-ops/claude/delegation.md`를 읽고 그 티어(GPT 우선·Claude 폴백)대로 배분한다. **harnie 실행 중에는 delegation.md를 읽지도 적용하지도 않는다.**
- **출력 간결**: 결론 + 필요한 근거만; 읽은 문서를 다시 인용하지 않는다; 출력이 큰 명령은 소스에서 필터링해 실행한다.

## 코딩 가이드라인

속도보다 신중함으로 기울인다; 사소한 작업은 재량. 비자명한 신규 코드는 `harnie-builder.md`도 함께 적용한다(종속 — 충돌 시 이 규칙이 이긴다).

1. **코딩 전에 생각하라.** 가정을 명시하고; 해석이 여럿이면 조용히 고르지 말고 제시하고; 더 단순한 접근이 있으면 말하라 — 필요하면 반박하라; 불명확하면 멈추고 물어라.
2. **단순함 우선 — 과설계는 결함이다.** 문제를 푸는 최소 코드: 요청 밖 기능 없음, 단일 사용 코드에 추상화 없음, 추측성 유연성·설정성 없음, 불가능한 시나리오의 에러 처리 없음. 조기 최적화 금지; DRY/SOLID는 rule of three 이후에만; 방어 코드는 신뢰 경계(외부 입력, API/DB/네트워크, 비신뢰 데이터)에서만. 200줄이 50줄이 될 수 있으면 다시 써라. 검사 질문: 시니어 엔지니어가 과복잡하다고 하겠는가?
3. **수술적 변경.** 요청이 요구하는 것만 건드린다: 인접 코드·주석·포맷을 "개선"하지 않고; 안 깨진 것을 리팩터링하지 않고; 기존 스타일을 따른다. 무관한 죽은 코드는 언급만 하고 지우지 않는다. 내 변경이 만든 고아(임포트·변수·함수)만 제거한다. 변경된 모든 줄이 사용자 요청으로 직접 소급돼야 한다.
4. **목표 주도 실행.** 작업을 검증 가능한 목표로 바꾼다("버그 고쳐줘" = 재현 테스트를 먼저 쓰고 통과시킨다); 다단계 작업은 짧은 단계→검증 계획을 밝힌다. 강한 성공 기준이 독립 루프를 가능하게 한다.
