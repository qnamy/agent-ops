# agent-teams.md — Agent Teams 사용법 (Claude Code only)

> 전역 CLAUDE.md의 트리거로 읽는다. Agent Teams는 **실험적** Claude Code 기능(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`)이며 대화형 세션에서만 동작한다. 헤드리스 `-p`는 플래그를 켜도 조용히 일반 서브에이전트로 폴백한다. Codex에서는 쓸 수 없다. 아래 사실은 Claude Code 2.1.245(2026-08) 기준 공식 문서를 따른다. CLI 메이저 업그레이드 시 재확인한다.

## 활성화

블로킹 E2E 검사 두 건이 2026-08-26에 통과했다(① 팀원 세션에서 플러그인 훅이 발화한다, ② 플래그가 켜져 있어도 이름 없는 디스패치는 일반 서브에이전트로 남는다). 이에 따라 플래그를 `~/.claude/settings.json`의 `env`로 승격했고, 이제 모든 대화형 세션에서 팀을 쓸 수 있다. harnie는 자체 팀 경로가 없다. 체인 단계는 plain 세션에서 돌고 리뷰는 별도 orca 세션에서 돈다.

## 라우팅: 직접 대 서브에이전트 대 팀

결정 순서다. 먼저 일치하는 항목이 이긴다.

1. 헤드리스 세션이거나 플래그가 꺼져 있으면 → 팀을 절대 쓰지 않는다.
2. 작고 순차적이거나 같은 파일에 집중된 작업 → 직접 처리하거나 서브에이전트 하나(공식 가이드: 팀은 토큰과 조율 비용이 상당히 더 든다).
3. 결과만 중요한 단일 작업(탐색, 단독 설계, 단독 리뷰) → **이름 없는 서브에이전트**.
4. 다음 5개 중 **3개 이상**이 '예'일 때만 팀을 구성한다. 멤버 간 직접 정보 교환이 필요하다 / 멤버들이 서로의 가설이나 설계를 반박해야 한다 / 자율 조율이 딸린 공유 작업 목록이 필요하다 / 여러 독립 도메인을 동시에 맞춰야 한다 / 기대되는 품질·속도 이득이 토큰+조율 비용을 넘어선다.

작업 도중 협업이 필요하다는 것을 발견한 서브에이전트는 팀을 구성하지 **않는다**(중첩 팀은 지원하지 않는다). 대신 `NEEDS-COLLAB: <reason>`과 부분 산출물 경로를 반환하고, 최상위 세션이 그 부분 산출물을 선행 작업으로 삼아 해당 단계를 팀으로 다시 돌린다.

## 하드 규칙

1. **일반 서브에이전트를 디스패치할 때는 `name`을 절대 넘기지 않는다.** 플래그가 켜진 세션에서는 이름을 붙여 스폰하면 조용히 반환 계약이 다른 팀원이 되어 버린다. 이 규칙은 팀 작업을 하지 않을 때도 그대로 적용된다.
2. **팀당 산출물 소유자는 한 명이다.** 단일 출력 파일은 팀원 한 명만 쓰고 나머지는 모두 읽기 전용 기여자다. 팀 단계에서는 소스코드 쓰기를 하지 않는다.
3. **완료는 두 조건을 함께 충족해야 한다**: 산출물이 디스크에 존재하고 리드가 그것을 읽었다는 것, 그리고 소유자의 결과 메시지를 받았다는 것이다. 유휴(idle) 알림만으로는 절대 완료가 아니다. 그 페이로드는 출력 없이 `type/from/timestamp/idleReason`뿐이며, `idleReason: "available"`은 '바쁘지 않다'는 뜻이지 '끝났다'는 뜻이 아니다.
4. **독립 리뷰어는 프로덕션 팀에 절대 합류하지 않는다.** 팀 안의 "챌린저/악마의 대변인"은 리뷰어가 아니라 탐색자 역할이다. 공식 리뷰 루프(예: harnie의 크로스모델 루프)로 들어가는 팀 산출물은 그대로 온전히 그 루프를 거친다. 팀 내부 토론은 같은 프로바이더 안에서 이뤄지므로 그 무엇도 대체하지 못한다. 이는 사후 수정에도 적용된다. 팀이 이미 크로스모델 리뷰를 통과한 문서를 수정할 때(그 리뷰의 발견사항을 판정하는 것도 포함된다) 수정된 델타는 같은 리뷰 경로(설계는 `software-design-review`, 코드는 `implementation-review`)를 다시 거친다. 팀의 종료 선언은 리뷰 종결이 아니다.
5. **팀 상태는 소모성이다.** 팀원은 `/resume`을 견디지 못한다. 복구는 디스크상의 산출물에서 단계를 재시작하거나, 부분 산출물에서 이어가는 서브에이전트 하나로 격하시키는 방식이다.
6. **팀원은 결정권자를 대신해 `[미결정]`을 확정하지 않으며, `_chain/`의 리뷰 파일이나 응답 파일을 절대 편집하지 않는다.** 디자이너 팀원은 미결 항목을 있는 그대로 기록하고 승계한다. 이는 설계 계약이다. 다만 그것을 확정하는 것은 팀이 아니라 지정된 결정권자의 행위다.
7. **상한과 스폰 위생**: 팀당 팀원 4명 이하, 팀 단계당 산출물 1개. 팀원을 스폰할 때는 항상 모델을 명시적으로 지정한다. 지정하지 않은 팀원은 리드의 모델을 물려받는데, 이는 대개 잘못된 선택이다. 추론 강도(reasoning effort)는 팀원별로 설정할 수 없고(리드의 것을 물려받는다), 역량 배분은 오직 모델 선택으로만 한다.
8. **리드의 종료 보고서는 팀 내부 상태를 풀어서 전달한다.** 각 발견사항은 그 내용으로 지칭한다. 사용자가 본 적 없는 원장 ID나 코드네임(F6, §5-4, "(가)")으로 지칭하지 않는다. 실제 이견의 개수를 명시한다. 이견이 0건이면 §Routing 테스트가 잘못 예측했고 서브에이전트 하나로 충분했을 것이라는 관측이므로, 보고서에 그렇게 적는다.

## 팀원 = 세 축

프로세스 역할(explorer / designer / builder / reviewer, 단 reviewer는 팀에서 금지) × 도메인 프로필(스폰 프롬프트로 주입하며 새 에이전트 정의는 절대 만들지 않는다) × 모델 등급:

| 등급 | Claude | GPT (Codex) | 용도 |
|---|---|---|---|
| T4 | fable | sol + high effort | 되돌릴 수 없는 아키텍처 결정, 모호한 인시던트 분석 |
| T3 | opus | sol | 복잡한 설계, 리뷰, 보안, 데이터 무결성 |
| T2 | sonnet | terra | 표준 설계, 구현, 리뷰 |
| T1 | haiku | luna | 탐색, 분류, 좁은 범위 검증 |

`delegation.md`의 등급은 여기서도 다른 곳과 마찬가지로 적용된다.

## 템플릿(이것들을 변형해서 쓰고, 고정된 조직도를 늘리지 않는다)

- **T-A 다중 도메인 계약 설계**: policy-analyst(explorer × policy × T2) + lead-designer, 산출물 소유자(designer × backend × T3–T4) + frontend-designer(designer × frontend × T2) + challenger(explorer × QA/reliability × T3). 출력: 설계 초안 하나 → 공식 리뷰 루프. 보안/마이그레이션/성능 explorer(T3)는 해당 위험이 있을 때만 추가한다.
- **T-B 경쟁 가설 인시던트 분석**: hypothesis-1..N(explorer × 가설 하나씩 × T2, **N≤2**. 4명 이하 상한이 걸린다: N + refuter + owner ≤ 4) + refuter(explorer × 반박 × T3) + incident-writer, 산출물 소유자(designer × synthesis × T3). 세 번째 가설은 다섯 번째 팀원이 아니라 owner의 synthesis에서 부차적으로 다룬다. 출력: 인시던트 보고서 하나.
- **T-C 개발 디스패치 계획**: 병렬 explorer들이 독립적인 사실을 확립하고, 디자이너 한 명이 이를 `orca-dispatch.md`용 유닛 카드 계획으로 통합한다. 각 카드는 파일 소유권, 저장소, 모델, effort, 프롬프트 참조 경로를 명시한다. 예: harnie 0.14 설계 세션은 조사 트랙 세 개를 병렬로 돌리고, 디자이너 한 명이 그 결과를 통합한 뒤 병렬 실행 계획을 만들었다. 팀 템플릿이 아니라 이 카드들이 디스패치 산출물이다.

## 사고 렌즈(스폰 프롬프트 템플릿 전용)

재사용 가능한 explorer 렌즈로, 스폰 프롬프트로 주입한다. 새 에이전트 정의는 절대 만들지 않고 내장된 읽기 전용 `Explore` 에이전트에 얹는다:

- `skeptic-challenger`: 초안의 가정을 공격한다. 실패 모드와 반례를 찾는다.
- `simplicity-advocate`: 요구사항을 충족하는 가장 작은 설계를 주장한다. 오버엔지니어링을 지적한다.
- `ops-risk`: 운영성을 점검한다. 장애 복구, 모니터링, 마이그레이션과 롤아웃 위험이다.

팀당 렌즈는 최대 1~2개이며, 팀 구성이 이미 정당화된 경우에만 추가하고, 요청이 지목한 판단 축과 헌장이 일치하는 렌즈만 추가한다. 단일 축 임무(예: 오버엔지니어링 사냥)에는 그 축을 주장하는 렌즈만 붙인다. 반대 축 렌즈는 사용자가 범위를 넓힐 때만 합류한다(2026-09 관측: 오버엔지니어링 패스에 붙은 `ops-risk` 렌즈가 낸 발견 23건 중 13건이 임무 범위 밖이었다).

렌즈는 주장만 한다. 판정은 절대 내리지 않으며, 렌즈 간 토론은 어떤 리뷰 라운드도 대체하지 않는다(하드 규칙 4). 이 계약은 렌즈의 스폰 프롬프트에도 다시 적어 둔다. **주장만 한다. 판정 없음, 수정 초안 없음, 문서 편집 없음. 출력은 각각 구체적인 시나리오가 딸린 발견사항이다.** 이 파일에만 존재하는 렌즈 계약은 스폰 시점에 사라진다. 렌즈를 실제 에이전트 정의로 승격하는 것은 실사용 약 3건이 그럴 가치를 입증한 뒤에만 한다(3의 법칙).

## 알려진 한계(공식 문서 + 2026-08 E2E, 이를 감안해 설계한다)

중첩 팀은 없다. 세션당 팀은 하나다. `/resume`은 진행 중이던 팀원을 복원하지 않는다. 진행 중인 팀원은 백그라운드 서브에이전트를 스폰할 수 없다. 팀원 메시지와 유휴 알림은 리드의 턴 경계에서만 전달된다. 턴 도중인 리드는 아무것도 받지 못하며(결과가 필요하면 디스크에서 산출물을 직접 가져온다), 팀원은 전달 여부를 확인할 수 없다. 리드 쪽에서도 팀원 쪽에서도 공유 작업 목록 도구는 관측되지 않았다(2026-08 E2E). 세션 도중 바뀐 훅 설정은 즉시 적용되지 않지만 재시작 없이 나중에 반영될 수도 있다(재적재 트리거는 미확인, 2026-08 E2E). 방금 바꾼 훅이 살아 있다고 절대 가정하지 말고 직접 발화시켜 확인한다. 서브에이전트 정의를 참조하는 팀원은 그 정의의 `tools:`와 `model:`은 적용하지만 `skills:`나 `mcpServers:`는 적용하지 **않는다**.
